# PRD — 영어단어 도장 콕! (가칭)

> 한자 도장 콕!의 자매 게임. 2026-07-30 작성.

---

## 1. 배경 · 대상 · 목표

**배경.** `index.html`로 만든 「한자 도장 콕!」이 동작 검증까지 끝났다. 같은 메커니즘(떠다니는 도장을 콕 찍어 정답을 고른다)을 영어단어에 그대로 적용하고 싶다.

**대상.** 영어 단어를 다시 다지고 싶은 성인. 한자판 README의 대상("한자를 잘 모르는 성인")과 동일한 가정이다.

> 자녀(2022년생·2024년생)는 아직 영어 읽기 전이라 v1 대상이 아니다. 아동용은 단어를 이미지·음성으로 제시해야 하므로 별도 기획이 필요하다.

**목표.** 한자판의 검증된 게임 루프를 재사용해, 어휘 데이터만 교체한 정적 단일 HTML 게임을 만든다.

---

## 2. 원래 질문에 대한 답 — 새로 정할 건 하나뿐이다

한자 게임의 난이도는 **이미 두 축으로 분리**되어 있다.

| 축 | 무엇 | 코드 위치 |
|---|---|---|
| **A. 어휘 난이도** | 급수 8→4, 누적 slice | `GRADE_BOUNDARIES` [index.html:673](index.html:673), `HANJA.slice(0, n)` [index.html:914](index.html:914) |
| **B. 기계적 난이도** | 선택지 수 3→9, 제한시간 9.0→3.5초, 도장 이동속도 | `LEVELS[1..12]` [index.html:676](index.html:676) |

**축 B는 언어와 완전히 무관하다.** 손댈 필요 없이 그대로 넘어온다. 콤보·하트 3개·8문제마다 단계 상승([index.html:1085](index.html:1085))·잉크 splat·틀린 문제 복습·결과 공유·PWA 홈화면 추가도 전부 재사용이다.

→ **"영어단어는 어떻게 단계를 구분하면 좋을까"는 축 A 하나만의 문제다.** 이걸 명확히 해두면 기획 범위가 크게 줄어든다.

> **단, 축 B의 수치는 재튜닝 후보다 — 시간뿐 아니라 선택지 수도.** 한자 1자는 흘긋 보고 인지하지만 영어 단어와 한국어 뜻 문구는 **하나하나 읽어야** 한다. 12단계는 `choices:9, time:3.5`인데, 움직이는 텍스트 도장 9개를 3.5초에 읽는 건 한자 9자를 훑는 것과 난이도가 다르다. 값 **구조**는 유지하되 제한시간과 최대 선택지 수(9 → 7 하향 검토)를 플레이테스트로 조정한다.

## 3. 축 A 설계: 영어단어 등급 체계

### 3-1. 판정 기준을 먼저 정한다

한자가 쉬웠던 진짜 이유는 급수 체계가 교육적으로 우수했기 때문이 아니라, **배정한자가 "단어별 등급이 붙은, 열거 가능한 공개 목록"이었기 때문**이다. 그러므로 선택 기준은:

> **단어별 등급이 태깅된 기계판독 데이터를, 단일 정적 HTML에 넣어 배포할 수 있는가.**

### 3-2. 후보 4개 실사 결과

| 후보 | 단어별 등급 태그 | 형식 | 라이선스 | 판정 |
|---|---|---|---|---|
| **Oxford 3000/5000** | ✅ A1~C1 | ❌ PDF만 | ❌ © Oxford University Press, 재배포 조건 미명시 | **✗ 탈락** |
| **교육부 기본어휘 3,000** (2022 개정, 고시 제2022-33호 별책14 254~290쪽) | △ 사실상 flat 3,000 — 교육과정의 학년군 구분은 *신출 어휘 **수*** 제한이지 단어별 태그가 아님 | ❌ PDF만 | ✅ 공공저작물 | **△ 보조** |
| **CEFR-J Wordlist** (openlanguageprofiles/olp-en-cefrj) | ✅ A1~B2, 행마다 태그 | ✅ CSV | ✅ 연구·상업 이용 무료(**출처표기 필수**), Tono Lab @ TUFS — 단, 근거는 GitHub 미러 README (아래 주의) | **✅ 채택** |

>
> **미확인 2.** 교육부 목록에 초등 권장 어휘 `*` 표시가 있는지 확인 못 했다(PDF 접근 실패). 있다면 2단 구분은 가능하지만, CSV 대비 PDF 파싱 비용이 남는다.

## 4. 데이터 스키마 — 한자와 결정적으로 다른 지점

**한자는 거의 1:1 대응이다.** 한 글자에 훈음 하나. 그래서 `buildDistractors`의 문자열 완전일치 중복 제거([index.html:868–889](index.html:868))만으로 충분했다.

**영어는 아니다.** 새로운 실패 모드 두 개가 생기고, 이건 구현 문제가 아니라 **스키마 문제**라 지금 정해야 한다.

### 4-1. 동의어 충돌 — 치명적

> 문제: `아름다운` → 보기에 **beautiful**(정답)과 **lovely**(오답)가 함께 뜬다.
> lovely를 눌러도 틀린 게 아닌데 오답 처리된다. 학습 도구의 신뢰가 무너진다.

**해결: 동의어군 id.** 같은 군의 단어는 한 문제에 절대 동시 출현시키지 않는다. 충돌하는 단어에만 id를 달고 나머지는 `0`이므로 데이터가 가볍다(스키마는 4-4절).

```
beautiful 아름다운 [7]   ┐
lovely    사랑스러운 [7]  ├─ 7번군: 셋 중 하나만 화면에 오른다
pretty    예쁜      [7]   ┘
big / large / huge → 3번군,  begin / start → 4번군,  angry / mad → 5번군
```

`buildDistractors`가 정답의 군 id를 보고 같은 군을 오답 후보에서 배제하도록 확장한다. 두 모드(영어→뜻, 뜻→영어) 모두 같은 테이블로 커버된다.

### 4-2. 다의어(polysemy)

`run`, `light`, `spring`, `back`은 보여줄 뜻이 하나로 정해지지 않는다.

**실측 규모:** A1 1,164행 중 **94개** headword가 품사 2개 이상. A1+A2 누적 **245개**.
예시: `back`, `change`, `clean`, `close`, `answer`, `brush`, `catch`, `all right`…

| 안 | 내용 | 평가 |
|---|---|---|
| **(a)** CSV의 `pos` 컬럼을 화면에 병기 — "달리다 **(동)**" / "달리기 **(명)**" | 데이터에 이미 있어서 **공짜**. run/verb와 run/noun을 별개 문항으로 쓸 수 있음 | **✅ 권장** |
| (b) v1에서 다의어 제외 | 안전하지만 흔한 단어가 대량 빠짐 | (a) 후에도 애매한 소수에만 적용 |
| (c) 뜻을 2개까지 표기 | 도장이 좁아 가독성 붕괴 | ✗ |

→ **(a) 기본 + 잔여 소수에 (b)**

### 4-3. 정제 필요 항목 (A1 실측)

| 항목 | 개수 | 처리 |
|---|---|---|
| slash 변이형 (`email/e-mail/E-mail`, `favorite/favourite`) | 26 | 미국식 하나로 정규화 |

| 채택 | 행수 | | 제외 | 행수 | 사유 |
|---|---|---|---|---|---|
| noun | 631 | | pronoun | 47 | `it`, `they` — 한국어 뜻 4택으로 성립 안 됨 |
| adjective | 148 | | determiner | 31 | `a`, `the` |
| verb | 134 | | preposition | 30 | `of`, `at` — 뜻이 문맥 의존 |

→ v1 실사용 풀 **988행**(정제 후 900 내외 예상). 규모로 적당하다.

### 4-4. 가장 큰 미해결 작업 — 한국어 뜻

검토한 **모든 목록이 영어 전용**이다. 배정한자는 훈음이 붙어 있었지만, 한국어 뜻이 붙어 오는 영어 등급 목록은 없다.

**학습 도구에서 틀린 뜻은 빠진 단어보다 나쁘다.** 그래서 뜻 부착 + 검수를 **독립 마일스톤**으로 잡고, v1 범위를 3,000+가 아니라 한 등급 규모로 좁힌다.

```js
// 최종 엔트리 형태 (HANJA와 대칭) — 5번째 필드는 동의어군 id (없으면 0)
const WORDS = [
  ["apple",     "사과",   "명", 0],
  ["run",       "달리다", "동", 0],
  ["run",       "달리기", "명", 0],
  ["beautiful", "아름다운", "형", 7],
  ["pretty",    "예쁜",    "형", 7],   // ← 7번군: 한 문제에 같이 안 나옴
];
```

**동의어군 id는 뜻을 쓰는 그 순간에 기록한다.** 사후에 900행을 눈으로 훑어 충돌쌍을 찾는 방식은 반드시 놓친다(9절 참고).

## 5. 화면 · 메커니즘 차이

**스탬프 폭.** 한자는 정사각 고정(`STAMP_SIZE`), 뜻/음 모드도 148×68 고정([index.html:306](index.html:306))이다. 영어는 `go`와 `responsibility`의 길이 차가 커서 **내용에 맞춘 가변폭(min/max 제한)** 이 필요하다. 또는 v1 단어 길이 상한을 둔다.

**모드.**
- `word2meaning` — 영어 → 뜻 (한자판 `hanja2word` 대응)
- `meaning2word` — 뜻 → 영어 (한자판 `word2hanja` 대응)
- **v2: `listen2word` — 듣고 찾기.** Web Speech API TTS로 단어를 읽어주고 영어 도장을 찾는다. **한자에는 없고 영어에만 있는 축**이며 브라우저 내장 API라 구현 비용이 거의 없다. 이 게임만의 새 가치.

**비목표(non-goals).** 스펠링 타이핑(도장 콕 메커니즘과 충돌), 문장·문법 문제, 발음 채점.

**포함**
- A1 등급 1개 · 명사+동사+형용사+부사 · **뜻 검수 완료 900행 내외**

- **출처 표기(라이선스 의무)** — CEFR-J 라이선스가 출처표기를 요구한다. 한자판이 `footer.hint`에 "한국어문회 8급~4급 배정한자 1,000자 기준"을 넣은([index.html:387](index.html:387)) 그 자리에 동일하게 넣는다:
  > `로컬 개인용 · 어휘 등급: CEFR-J Wordlist (Tono Lab, TUFS) 기준`

**제외**
- A2~B2 (뜻 데이터 준비되는 대로 증분 추가 — 누적 구조라 배열 뒤에 붙이고 boundary만 갱신하면 됨)
- TTS 모드(v2 확정) · 기능어 · 다어절

> v1에 등급이 하나뿐이면 시작화면의 "급수 선택" UI에 고를 게 없다. 등급 선택 영역은 **A2~B2를 비활성 상태로 노출**해(A1만 선택 가능) 확장 예정임을 드러낸다. 한자판의 `grade-grid`([index.html:383](index.html:383)) 구조를 그대로 쓰면 된다.

## 7. 파일 · 배포

**새 파일 `english.html`로 분리한다.** 같은 페이지에 모드 토글을 넣는 건 반대다 — `index.html`에 한자 전제가 박혀 있다(`hanja-clue` 클래스, `clue` 렌더링 분기 [index.html:1002](index.html:1002), `HANJA` 배열 구조, `stamp.hanja` 필드).

**manifest·아이콘 별도 세트 필수.** 현재 `manifest.json`은 한자 전용이고(`name: "한자 도장 콕!"`, `start_url: "./index.html"`), `apple-mobile-web-app-title`도 `한자도장콕`([index.html:9–16](index.html:9))이다. 안 나누면 "홈 화면에 추가"가 충돌한다.

**결정 —** 기존 `nolwoo/hanja-nori` repo에 `english.html`을 추가한다. repo 이름이 한자 전용이라 어색하지만, 게임이 더 늘어날 때 이름 변경 + 허브 페이지를 검토한다(지금은 불필요한 작업).

추가할 파일:
```
english.html              ← 새 게임 (index.html은 그대로 둔다)
manifest-english.json     ← name/short_name/start_url/theme_color 별도
icon-en-192.png, icon-en-512.png, apple-touch-icon-en.png, favicon-en-32.png
```

> **동의어군을 여기서 같이 단다.** "이 뜻을 보고 학습자가 떠올릴 다른 단어는?"이라는 판단은 뜻을 쓰는 순간 어차피 하고 있다. 이걸 뒤로 미루면 900행을 눈으로 훑어 쌍을 찾아야 하는데, 그 방식은 반드시 놓친다. 확신이 낮은 항목은 `⚠` 주석으로 표시.

**2. 사용자 검수 — 2단 구조** (전량 정독 아님)

| 대상 | 규모 | 방식 |
|---|---|---|
| 다의어(품사 2개 이상) + `⚠` 표시 항목 | 94 + α | **전량 확인** |
| 구체 명사 등 나머지 | ~700 | **표본 점검** (틀리기 어려운 구간) |

이 단계 통과 없이 구현에 들어가지 않는다.

**3. 기계적 중복 스캔** — 뜻 컬럼을 `sort | uniq -d`로 돌려 **완전히 같은 뜻 문자열**(예: `apple`/`apology` 둘 다 "사과")을 잡아낸다. 사람 눈이 아니라 스크립트가 할 일이다. 1번에서 단 의미 기반 동의어군과 상호 보완 관계.

**4. `english.html` 구현** — `index.html`을 복제해 데이터 · 클루 렌더링 · 스탬프 가변폭 · `buildDistractors` 동의어군 확장만 교체.

**5. manifest·아이콘 세트 + 출처 표기 footer 추가.**

**6. 플레이테스트 → 축 B 제한시간·최대 선택지 수 재튜닝** (2절).
